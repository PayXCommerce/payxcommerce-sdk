# PayXCommerce for osCommerce 4

Hosted-checkout payment module tested against osCommerce 4.14 build 63493. The store never handles card details. This module is separate from the OpenCart extensions.

## Package and installation

Run `bash scripts/build-oscommerce4-package.sh` from the integrations repository. The generated `dist/plugins/payxcommerce-oscommerce4.zip` contains the two module files under `lib/common/modules/orderPayment/` and the bundled checkout icon under `images/payxcommerce/`. Back up the store, extract the ZIP at the osCommerce 4 application root, then use Admin → Modules → Payment → PayXCommerce → Install for the relevant storefront/platform. This is a file-upload package, not an osCommerce administrator ZIP installer. Do not extract it under `admin/` or under another `lib/` directory.

Keep the two module files and bundled image together. The module creates `payxcommerce_order` and `payxcommerce_event` tables on installation. Do not drop these tables while orders or callback retries still depend on them. Before upgrading, back up the store database and module files. Replacing the two PHP files does not change existing credentials or order mappings; review schema changes in the release before an upgrade. Visit the PayX module settings after upgrading: osCommerce adds the new express toggle as `False` for existing installations (opt in when ready) and replaces only PayX status-selector metadata so ungrouped statuses can be edited. Existing sort orders and status values are not rewritten.

## Configuration

In the payment module settings, select `test` or `live`, the matching PayX API URL, and either HMAC public/secret keys or Developer App client ID/secret. Set the webhook signing secret for the same mode. API and webhook secrets use osCommerce's encrypted module configuration storage. Set distinct, valid order statuses for pending, paid, failed, cancelled, partially refunded, refunded, and chargeback. The module stays unavailable at checkout until all required credentials and statuses are configured. Test keys cannot create live-mode requests.

New installs use display sort order `1`; an existing store's chosen order is retained. osCommerce's checkout radio order follows its installed-module list, while the numeric sort order controls the inline checkout-init buttons; changing the number alone does not reorder other payment radios. The first setting, `Enable PayXCommerce express checkout`, independently controls a button beside the cart's checkout action. It defaults on for a new install and off for an upgrade, so existing carts do not gain a new action without review. The button opens the normal osCommerce checkout with PayX preselected. It does not create an order, contact PayX, skip address/shipping/tax/terms checks, or handle card data. Normal checkout PayX selection remains available with the button on or off. An invalid enabled status mapping is rejected before any setting is saved, and leaving a secret field blank preserves its stored value.

The express button carries only button-scoped CSS in its returned markup. It is 50px high, fills its checkout container like a standard PayPal button, has no border and white text, and loads the icon from the package's relative `images/payxcommerce/` path. It does not load an icon from the PayXCommerce website. Keep the bundled image when upgrading.

The module sends the store's `callback/webhooks.payment.payxcommerce` endpoint on each request. This route must be reachable over HTTPS by PayX without a store login or HTTP Basic Auth, but should have normal perimeter rate limits. The module authenticates each callback with the `X-PXC-Event-ID`, `X-PXC-Timestamp`, and `X-PXC-Signature` headers and the raw request body. Configure the same callback URL in PayX merchant webhook settings as a fallback. Never use a Production merchant key on a non-Production osCommerce installation.

## Payment lifecycle

After osCommerce saves the order, the module creates one PayX payment request using a persistent idempotency key, saves the returned request reference and HTTPS checkout URL, creates one pending osCommerce payment ledger row, clears the completed cart, and redirects to PayX. Browser returns only display a pending message; they never mark an order paid. A signed success callback must bind to the stored request, environment, request amount and currency before marking the order and debit ledger paid. Replayed event IDs and repeated success events cannot duplicate the financial transition. A late failure/cancellation cannot undo a settled payment.

Signed refunds create separate credit ledger rows keyed by refund reference. Partial refunds change the order to the configured partial-refund status; only cumulative refunds equal to the original payment produce full-refund status. Chargeback/dispute-loss events change to the configured chargeback status. Invalid, unmatched, or out-of-order callbacks return a retryable error rather than accepting an unrecorded financial change. All callback writes use a database transaction.

The selected PayX merchant must permit the order's currency, customer country, amount and configured gateway. If PayX rejects a request, the order remains pending and the checkout does not claim success. Diagnose the explicit API error in PayX API logs and the osCommerce application log; do not weaken merchant limits or routing to force checkout through.

## Validation

Run `php plugins/oscommerce4/tests/standalone.php` for deterministic configuration, decimal, URL, and webhook-signature checks. On a separate non-Production osCommerce 4 store, verify status selectors include ungrouped statuses; repeat saves of sort order and unrelated settings preserve seven distinct mappings and secrets; invalid enabled mappings return an admin error without a partial save. Check cart express ON/OFF and empty cart; with express ON, confirm PayX is preselected in normal checkout, missing contact/address/shipping data still blocks progress, and only a validated saved order creates one hosted request and ledger row. Verify normal guest checkout, return, signed success/failure/refund callbacks, mismatched amount rejection, duplicate replay, and a late failure after success. Do not complete an actual gateway payment merely to test the connector; use an approved Sandbox fixture.
